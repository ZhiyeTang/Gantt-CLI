# 按任务需要选择执行流程

状态：implemented。2026-09-07 完成四项本地任务及独立规格、规范审查；`npm test` 的 55 项真实 Git/CLI 集成测试全部通过。

## Problem Statement

所有实现任务都被要求登记并创建 worktree，使轻量修改承担了完整调度成本。范围重叠的任务即使已经协调仍被阻塞；未跟踪文件被统一视为不干净，妨碍正常合并。Agent 还必须手动串联合并、清理和完成命令，验证失败时现场可能已经被删除。

用户需要 Agent 自主选择适合任务的流程，在充分协调后并行开发，并用一个可重试的命令完成受管任务，同时保全已有工作和本地文件。

## Solution

Agent 在修改前判断任务是否需要隔离或协作，并简述理由。轻量任务直接完成；受管任务登记、调度并进入独立 worktree。允许 Agent 记录协调计划后自行放行重叠任务，目标分支合并保持串行。

Agent 提交任务变更后，调用统一收口入口，依次检查、合并、验证、保存需保留的文件、清理现场和标记完成。每一步失败都返回具体原因和下一步操作，修复后重新调用同一入口继续。

## User Stories

1. 作为用户，我希望范围明确、低风险且可直接验证的修改直接 inline 完成，以免为小任务创建分支和 worktree。
2. 作为 Agent，我希望自行判断任务轻重并简述依据，以免每次启动都请求用户批准。
3. 作为用户，我希望任务是否需要完整流程由协作和隔离需要决定，而不是由文件数量决定。
4. 作为 Agent，我希望轻量任务变复杂时升级为受管任务，并保留本任务已完成的改动。
5. 作为用户，我希望升级任务时保留原目录中已有的其他修改，不被混入或移走。
6. 作为用户，我希望原有本地配置不因未被 Git 跟踪而阻塞无关任务的合并。
7. 作为 Agent，我希望根据任务开始前的文件记录和显式声明区分任务产物与本地文件，而不是靠名称猜测。
8. 作为用户，我希望清理前自动保存已分类的本地配置和非交付文件，并得到可直接访问的保存路径。
9. 作为 Agent，我希望未分类的新文件列出明确的处理要求，分类后重跑收口，避免漏交新源码。
10. 作为用户，我希望被 Git 忽略的配置与未被忽略的配置一样得到保护。
11. 作为 Agent，我希望为重叠任务记录分工、合并顺序和整体验证方式后即可并行启动。
12. 作为用户，我希望路径重叠提示保留其协调价值，同时允许已协调的同模块或同文件任务并行。
13. 作为 Agent，我希望任务依赖与合并顺序分别表达，以免为了先合并 A 而阻止 B 提前开发。
14. 作为 Agent，我希望完成提交后只调用一次收口命令，就完成合并、验证、清理和状态更新。
15. 作为 Agent，我希望冲突、验证失败或进程中断后保留现场，修复后继续调用同一收口命令。
16. 作为用户，我希望完成状态对应实际交付证据，重复收口不会重复合并、重复删除或误报成功。

## Implementation Decisions

### 任务分流与升级

- 修改 Agent 集成规则，使分流发生在登记之前；inline 不创建 Requirement、Assignment 或 worktree，也不新增 inline 状态机。
- Agent 在已有上下文中记录修改前状态，并负责识别和转移本任务改动。首版不增加通用的脏工作区迁移服务。
- 自动升级必须先确保新 worktree 中的任务改动已保存并核对完整，再移除原目录中对应的任务改动；无法区分本任务与既有修改时保留原状并说明歧义。

### 本地文件与任务产物

- 开始前的文件记录提供来源证据；显式声明说明归属。两者都不能把未保存的修改变成可删除内容。
- 合并前检查与删除前检查采用各自的标准。目标目录中无关本地文件允许存在；会被合并覆盖的文件必须保留并报告冲突。
- 任务产物必须提交或明确分类为非交付内容；保存到其他目录不能代替应有的代码交付。
- 保存目录位于待删 worktree 之外，按 Assignment 区分；保持相对路径，返回保存位置。保存失败或目标内容冲突时保留原文件，不能覆盖其他内容。
- 保存范围覆盖已分类的未跟踪文件及 ignored 文件。不能将所有 ignored 内容视为可丢弃缓存，也不能默认复制整套依赖目录；其保留或可重新生成的归属需明确。
- 未分类的新文件、未提交的跟踪文件修改和存在独有 Git 数据的嵌套仓库继续阻止删除，返回具体路径和处理要求。
- 文件记录、分类与保存结果持久化到现有任务记录体系；不记录配置内容到提交、事件或终端输出。

### 并行协调

- 协调计划明确涉及哪些任务、如何分工、按什么顺序合并，以及如何验证整合结果。
- 调度和启动共同识别有效的协调计划；已协调的范围重叠可以放行，未经协调的重叠继续给出阻塞原因。
- 原有任务依赖继续决定能否开始工作；合并顺序仅约束收口顺序。
- 协调计划不授予未列入计划的任务通用豁免，也不放宽任务实际提交的路径范围检查。范围或参与任务改变后重新检查计划是否仍覆盖相关重叠。
- 各任务独立检出，目标分支上的合并和验证过程串行；沿用现有锁和 Git 能力，不新增后台调度服务。

### 自动收口与恢复

- 对外提供一个明确的收口入口；命令具体名称在实施时结合现有 CLI 统一确定。
- 收口复用现有交付证据和状态记录；只有检查、合并、验证、文件保全和清理全部成功才标记完成。
- 验证在合并后的目标工作区进行，并在删除任务 worktree 前完成。验证失败保留任务 worktree，Agent 可继续修复、提交并重试；失败不隐式回滚用户分支。
- 验证记录绑定所验证的目标提交；目标或源提交改变后必须重新判断并运行所需验证。没有配置验证命令时明确报告未运行项目验证，不伪称测试通过。
- 发生 Git 冲突时保留冲突现场和任务归属，Agent 解决后重跑入口。不能因为某个源提交已是祖先就直接认定本次收口完成。
- Git 操作成功但记录写入中断时，重试根据预先保存的操作意图和实际提交证据恢复；证据不足则保留现场并说明原因。
- 已完成任务再次调用收口入口返回已有完成结果；部分完成任务从可验证的进度继续。
- 不为保留旧的手工收口顺序而新增兼容层；低层命令是否保留取决于明确的诊断和修复用途，不能绕过完成条件。

## Testing Decisions

沿用现有测试框架，从 CLI 入口调用命令，在临时 Git 仓库中检查文件内容、Git 历史、执行结果和任务状态。测试用户可观察行为，不为内部辅助函数逐个建立测试，也不新增依赖。

| 场景 | 验收结果 |
| --- | --- |
| 轻量任务与执行中升级 | 指令明确先分流；行为演练覆盖已有无关修改与未提交任务改动，升级后两者都保留且归属正确 |
| 无关本地配置 | 合并成功，配置字节内容不变；同路径覆盖冲突时配置仍保留 |
| 已分类普通及 ignored 文件 | 收口返回保存路径，保存内容完整后才删除 worktree |
| 未分类新源码、保存失败或目标冲突 | 保留现场和文件，给出可操作提示，不标记完成 |
| 子模块和嵌套仓库 | 沿用现有文件与独有 Git 数据保护，不能因放宽未跟踪文件规则而丢失数据 |
| 同文件已协调任务 | 可同时调度和启动，合并遵循记录顺序；未协调任务和真实依赖仍受约束 |
| 正常收口及重复调用 | 一次完成检查到 done；重跑不重复产生合并或破坏保存内容 |
| 验证失败后修复提交 | worktree 保留，重跑整合修复并重新验证后才完成 |
| 合并冲突与记录写入中断 | 解决冲突或恢复执行后重跑同一入口，核对真实证据后继续 |
| 并发收口 | 不交叉修改目标工作区，不用过期验证结果标记完成 |

inline 分流由 Agent 执行，CLI 测试不能证明 Agent 在所有情境下都能正确判断；需要结合指令检查与上述行为演练验收。

## Out of Scope

- 自动代替 Agent 选择提交内容、撰写提交说明或解决语义冲突。
- 多个 Agent 共享同一个任务工作目录并同时写文件。
- 轻量任务的独立任务状态体系、后台守护进程、新数据库或新测试框架。
- 隐式推送、发布、删除任务分支或触发阶段归档。
- 为旧行为保留兼容层或迁移机制。
